# 定制化翻译软件 · 开发计划

> 本项目的核心目的不是"做出一个翻译软件"，而是通过实战把 Prompt Engineering、RAG、Tool Use、MCP、Agent 编排这些技术串联起来，最终具备为企业构建 Agent 系统的能力。
> 计划会随开发进度不断调整，本文档是当前阶段的共识记录，不是一成不变的规范。

---

## 一、项目背景

市面翻译软件的痛点：
- 只能直译，无法做句子结构分析、语法讲解等深度解析
- 词库老旧，且不开放接自定义 AI 模型接口，用几次就要求付费
- 希望做到：老词库 + 自定义 AI API + Prompt 定制化，三者结合

**开发方式**：使用 Claude Code 作为编码助手，采用"一边学习一边构建"的方式，不追求一步到位生成可用软件，而是每一步都要理解代码在做什么。

## 二、产品设计决策

### 2.1 输入形式
- 当前阶段：仅支持**纯文本**输入
- 暂不做：文档（docx/pdf）、网页翻译（留待后续扩展）

### 2.2 输出形式：结构化输出
不用一整段夹杂译文+解释的文本，而是让 AI 按固定 schema 返回结构化数据（JSON），每个字段独立可用，方便后续 UI 渲染和工具联动（如生成 Anki 卡片、导出 Markdown 笔记）。

**Phase2 最终确定的 detailed 输出结构**：

```json
{
  "translation": {
    "literal": "逐字直译结果",
    "meaning": "更自然的意译结果",
    "difference": "直译和意译的区别及各自适用场合"
  },
  "sentence_structure": [
    {
      "component": "主语 / 谓语 / 定语从句 / 虚拟语气 等",
      "original": "原文对应片段",
      "explanation": "详细语法解释"
    }
  ],
  "special_grammar": "虚拟语气、倒装、省略等特殊语法说明，没有则为空字符串",
  "vocabulary": [
    {
      "word": "重点单词 / 俚语 / 固定搭配",
      "type": "单词 / 俚语 / 固定搭配 / 惯用表达",
      "meaning": "含义和用法说明",
      "examples": ["例句1", "例句2"]
    }
  ],
  "overall_note": "整体评注：语气、使用场景、文化背景、近义表达程度差异等",
  "other_languages": {}
}
```

### 2.3 翻译模式：按需生成
通过参数控制返回内容的详细程度：

| 模式 | 返回内容 | 适用场景 |
|---|---|---|
| `quick` | 仅直译 | 整段/整篇快速翻译 |
| `detailed` | 直译+意译+句子结构+特殊语法+重点词汇+整体评注 | 单句/短语深度学习 |

CLI 调用方式：
```bash
python -m translator.cli "文本" --from 中文 --to 英文 --mode detailed
```

### 2.4 语言支持
- 当前支持：中英互译（`--from` 指定原文语言，`--to` 指定目标语言）
- 预留扩展：`DetailedResult` 里有 `other_languages` 字段（`dict[str, str]`），以后加日文/韩文等直接往里填，不需要改数据结构

## 三、技术架构决策

### 3.1 老词库的定位：RAG 检索源
词库不再是"翻译结果的来源"，而是**AI 翻译前的参考上下文**：
1. 老词库（如 CC-CEDICT 等开源词典）做向量化，建立可检索库
2. 翻译时先检索相关词条（尤其是多义词、专业术语）
3. 检索结果作为上下文注入 prompt，让 AI 结合语境判断，而非仅凭训练记忆直译

### 3.2 API Provider 抽象层

**决策更新**：实际调用走 **OpenRouter**（原因：统一计费入口、价格更划算，而非需要同时对比多家模型效果）。

OpenRouter 是聚合网关，对外接口**兼容 OpenAI 格式**，因此：
- 依赖包安装 `openai`（而非 `anthropic`），`base_url` 指向 OpenRouter：
  ```python
  from openai import OpenAI
  client = OpenAI(
      base_url="https://openrouter.ai/api/v1",
      api_key=os.getenv("OPENROUTER_API_KEY"),
  )
  ```
- 模型名要写成 `厂商前缀/模型名`，如 `anthropic/claude-sonnet-4.5`
- 返回结构走 `response.choices[0].message.content`（OpenAI 风格），与直连 Anthropic SDK 的 `message.content` 结构不同

因为当前只走 OpenRouter 一个入口，**provider 抽象层可以先简化**：阶段1只需扎实实现"OpenRouter provider"这一个，抽象层留好接口即可，以后要接别的服务商（如直连 Anthropic 官方 API 用某些独有功能）时再加新的 provider 实现类：

```python
translate(text, provider="openrouter")   # 预留接口，后续可扩展 "anthropic_direct" / "ollama" 等
```

由于目标是"划算"，**成本控制（缓存、token 用量统计）比最初设想的更重要**，是真正要在阶段0-8持续关注的点，而不只是顺手加的功能。

### 3.3 缓存机制：轻量、非全量
- **缓存粒度**：标准化后的单句/短语（去除多余空格、统一大小写），而非整段文本
- **区分是否缓存**：直译结果适合缓存（较稳定）；语法解释/风格化译文默认不缓存，或提供"强制重新生成"开关
- **失效策略**：LRU（最近最少使用）+ 过期时间，避免无限增长
- **缓存 key 包含模型版本 + prompt 版本**：换模型或改 prompt 后，旧缓存自动失效
- 存储：本地 SQLite 即可，无需引入 Redis

### 3.4 翻译历史存储
用 SQLite 存储，为后续 RAG（检索历史翻译/术语一致性）打基础：

```
translations 表字段：
- id
- timestamp
- source_text
- target_lang
- mode              (quick / detailed)
- literal_translation
- grammar_analysis  (JSON)
- explanation
- model_used
- tokens_used
```

## 四、技术栈

- **语言**：Python（RAG、embedding、Anthropic SDK、MCP SDK 生态都比较成熟）
- **存储**：SQLite（翻译历史 + 缓存）
- **向量检索**：待阶段4确定（如 chromadb）
- **架构形态**：**暂不做前后端分离**
  - 阶段0-5：全部用 CLI（命令行），专注打磨"大脑"逻辑，不被前端分心
  - 阶段6-7：MCP 本身是 client-server 架构，会自然长出雏形
  - 阶段8：视需求决定是否做网页 UI（可选 Streamlit/Gradio 快速原型，或 FastAPI 正式前后端分离）

### 阶段4：RAG 向量检索 ✅

**新增文件**：

**修改文件**：
- `dictionary/retriever.py` — 精确匹配基础上加一层语义检索，合并去重后返回
- `core.py` — 翻译前检索词典+历史双源上下文注入 prompt，翻译后把结果存入历史
- `config.py` — 新增 embedding、ChromaDB、历史检索相关配置
- `prompts.py` — detailed 模式新增规则：字段内引用原文短语用中文引号「」而非英文双引号，避免破坏 JSON 结构

> **踩坑记录1**：`dictionary/store.py` 的 `index_exists()` 最初只判断数据库文件存不存在，
> 没判断表里有没有数据。`dictionary.db` 文件其实早就存在（内容是空的），
> 导致索引建立逻辑一直被跳过，精确匹配长期失效却没报错，验证阶段才发现。
> 修复方式：改成真正查 `entries` 表的行数。

> **踩坑记录2**：detailed 模式下模型返回的 JSON 里，字段内容偶尔会带未转义的英文双引号
> （例如解释里写 `"the team's kernel optimization works"`），导致 `json.loads()` 解析失败。
> 双管齐下解决：prompt 里明确要求引用原文短语用中文引号「」；`core.py` 的 `_parse_json()`
> 增加 `json_repair` 库做兜底修复，两层都失败才真正抛错。

> **踩坑记录3**：`history/retriever.py` 的 `retrieve_similar()` 会把内容完全相同的历史记录
> （同一句话被反复翻译产生的重复行）一起召回，注入 prompt 时造成冗余。
> 修复方式：检索阶段按 `(原文, 译文)` 去重，但 SQLite/ChromaDB 里的原始记录不做任何清理——
> 因为每条记录对应一次真实的 API 调用和真实的 token 花费，是成本统计要用的原始流水，
> 去重应该发生在"喂给 prompt 的参考资料"这一层，不应该发生在"记账"这一层。

> **设计说明**：词典向量化时用词条的英文释义做 embedding，查询时用完整中文原句做 embedding，
> 属于跨语言语义检索，实测召回质量一般（不如同语言检索精准），留待后续阶段优化，
> 不影响当前"能召回精确匹配之外的相关词条"这一功能性目标。

详细步骤见 [`docs/phase4-steps.md`](docs/phase4-steps.md)

### 阶段5：自定义工具（Tool Use）✅

把 Phase3/4 "每次翻译都固定查词典+历史"的**被动检索**，
改成"告诉模型有哪些工具，由它自己决定查不查、查什么"的**主动决策**。

**新增文件**：
- `tools/definitions.py` — 两个工具的 JSON Schema（OpenAI function calling 标准，OpenRouter 兼容）
- `tools/executor.py` — 工具执行器，核心原则是**永不抛异常**，失败也转成给模型看的文本

**修改文件**：
- `providers/base.py` — 拆成 `chat()`（单轮，Phase1-4）和 `chat_with_tools()`（多轮，Phase5）两个抽象方法
- `providers/openrouter.py` — 实现两个方法；异常处理抽成 `@handle_api_errors` 装饰器复用
- `core.py` — 新增工具调用循环 `_translate_detailed_with_tools()`；
  原 Phase4 实现改名 `_translate_detailed_fixed()` 保留为 `--no-tools` 的实现；
  两条路径共用的结果组装逻辑抽成 `_build_and_save_detailed()`
- `cli.py` — 新增 `--no-tools` 开关，detailed 输出里显示用了哪些工具、绕了几轮
- `prompts.py` — 新增 `DETAILED_TOOLS_SYSTEM_PROMPT`（在原 prompt 后拼接工具说明，不重写，保证两条路径共用同一套 JSON 格式要求）
- `schemas.py` — `DetailedResult` 新增 `tools_used` / `tool_rounds` 两个可观测性字段

**关键设计决策**：
- **只在 detailed 模式启用工具**。quick 模式保持固定检索——工具调用的 token 是累积增长的
  （每轮都要重发完整消息历史），quick 追求快和省，不值得为它多花几轮
- **接口拆分而非加可选参数**。若在 `chat()` 上加 `messages=None, tools=None`，
  会出现"传了 messages 后 system_prompt 就被忽略"的参数互斥设计，调用方光看签名不知道怎么用

> **踩坑记录1**：`lookup_dictionary` 对英文输入必然失效。CC-CEDICT 的 SQLite 索引只按中文建列，
> 英文只在 `definitions` 列里，而 `lookup()` 查的是 `WHERE simplified = ? OR traditional = ?`，
> 连 `bus` 这种基础词都查不到。而原工具描述里写着「或一个英文单词/短语」，
> 等于在诱导模型做注定失败的调用，英译中每次都白绕一轮。
> 修复方式是改描述（明确声明只支持中文词条），实测输入 token 从 2212 降到 1068，**降幅 52%**，
> 一行执行逻辑都没改。

> **踩坑记录2**：`search_history` 几乎不被模型主动调用（口语句、习语句、含术语的同批文档句都不调，
> 偶尔会调但不稳定）。改描述（方案A）没能改变行为，说明这不是描述问题，而是架构问题：
> 检索类工具天然被模型低估——它无法在调用前预判收益，而代价是确定的一整轮请求。
> 顺带算出一笔账：`search_history` 全在本地跑不花钱，但"让模型决定要不要查"要花一整轮 API 请求，
> **用付费 token 去决定要不要做一件免费的事，经济上是亏的。**

> **待第二轮重新设计**：句子级"相似"检索本身可能就是错误的抽象。
> 相似度 0.982 的两句（"我今天很累" / "我今天非常疲惫"）差异恰恰在必须译出的细微处，
> 注入历史参考反而会锚定模型、抹平差异。CAT 工具（Trados/memoQ）早已把
> **翻译记忆库 TM**（只在 95%+ 匹配时有价值）和**术语库 Glossary**（任何时候有价值）拆成两件事。
> 真正需要跨句保持一致的是术语，不是整句。方向：新增术语库、句子级阈值提到 0.95+、
> 重新把历史记录定位为成本统计和用户回看。详见 `docs/phase5-steps.md`。

**Phase5 最有价值的两个对照实验**：

1. **把工具描述砍成极简的 `"查词典"`**（schema 210 → 58 tokens）。
   结果与预期相反：模型不是开始乱调，而是**彻底不调了**（习语句 5/5 调用 → 0/4 调用，
   改回详细版立即恢复）。
   **结论：工具描述的作用是"授权调用"——告诉模型什么情况下花一轮请求调它是划算的，
   而不只是"防止乱调"。** 而且这种失效是静默的：不报错、译文照常，
   但工具永不触发，还在为 schema 付钱。三方对比后更狠的结论是：
   **描述糟糕的工具比不加这个工具还差**（比 `--no-tools` 多花 75% token，拿到的参考信息为零）。

2. **把 `DICT_DB_PATH` 指向不存在的目录，制造真实工具故障**。
   程序没崩、模型没重试、译文质量与词典正常时完全一致。
   **结论：容错必须代码层和 prompt 层配套。** 只有代码兜底而没在 prompt 写"失败别重试"，
   模型可能反复调用撞满轮数上限；只有 prompt 规则而代码往上抛异常，
   程序在模型读到规则之前就已经崩了。

**成本实测（deepseek/deepseek-v4-pro）**：

```
基础翻译（--no-tools）              ≈  570 tokens
+ 开启工具的"入场费"（schema+说明）  ≈  550 tokens   ← 不管用不用都付
+ 每多绕一轮工具调用                ≈ 1350 tokens   ← 整个消息历史重发一遍
```

触发工具的句子约 **4.3 倍**成本，完全没触发工具的句子也要 **2 倍**。
`ALL_TOOLS` 序列化后约 471 tokens，两轮就是 942——占某次实测总输入的 **38%**，
纯粹在反复告诉模型"你有什么工具"。
另外**输入 token 可预测、输出 token 不可预测**（同句重复跑实测波动 1.9～2.8 倍），
做成本控制时能优化的只有输入侧。
