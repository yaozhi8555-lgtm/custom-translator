# 定制化翻译软件 · 开发计划

> 本项目的核心目的不是"做出一个翻译软件"，而是通过实战把 Prompt Engineering、RAG、Tool Use、MCP、Agent 编排这些技术串联起来，最终具备为企业构建 Agent 系统的能力。
> 计划会随开发进度不断调整，本文档是当前阶段的共识记录，不是一成不变的规范。

---

## 一、项目背景

市面翻译软件的痛点：
- 只能直译，无法做句子结构分析、语法讲解等深度解析
- 词库老旧，且不开放接自定义 AI 模型接口，用几次就要求付费
- 希望做到：老词库 + 自定义 AI API + Prompt 定制化，三者结合

**开发方式**：使用 Claude Code 作为编码助手，采用"一边学习一边构建"的方式，不追求一步到位生成可用软件，而是每一步都要理解代码在做什么。

---

## 二、产品设计决策

### 2.1 输入形式
- 当前阶段：仅支持**纯文本**输入
- 暂不做：文档（docx/pdf）、网页翻译（留待后续扩展）

### 2.2 输出形式：结构化输出
不用一整段夹杂译文+解释的文本，而是让 AI 按固定 schema 返回结构化数据（如 JSON），例如：

```json
{
  "original": "我今天很累。",
  "literal_translation": "I am very tired today.",
  "grammar_analysis": {
    "subject": "我 (I)",
    "predicate": "很累 (very tired)",
    "structure": "主谓结构"
  },
  "explanation": "日常口语化的疲惫表达",
  "alternative_translations": ["I'm exhausted today.", "I'm really tired today."]
}
```

**好处**：每个字段独立可用，可以分别渲染到 UI 不同区域（译文加粗展示、语法解析做成折叠面板、备选译文做成可点击标签），也方便后续被其他工具消费（如自动生成 Anki 记忆卡片、导出 Markdown 笔记），无需再对文本做脆弱的正则解析。

### 2.3 翻译模式：按需生成
通过参数控制返回内容的详细程度：

| 模式 | 返回内容 | 适用场景 |
|---|---|---|
| `quick` | 仅直译 | 整段/整篇快速翻译 |
| `detailed` | 直译 + 语法解释 + 整体解释 | 单句/短语深度学习 |

不同模式对应不同的 system prompt 模板和不同的输出 schema。

## 三、技术架构决策

### 3.1 老词库的定位：RAG 检索源
词库不再是"翻译结果的来源"，而是**AI 翻译前的参考上下文**：
1. 老词库（如 CC-CEDICT 等开源词典）做向量化，建立可检索库
2. 翻译时先检索相关词条（尤其是多义词、专业术语）
3. 检索结果作为上下文注入 prompt，让 AI 结合语境判断，而非仅凭训练记忆直译

### 3.2 API Provider 抽象层
从一开始就做统一的 provider 接口，不绑定单一模型服务：

```python
translate(text, provider="claude")   # 也可以是 "openai" / "ollama" 等
```

好处：便于后续切换/对比模型，也是企业级 Agent 系统常见设计模式，提前练手。

### 3.3 缓存机制：轻量、非全量
- **缓存粒度**：标准化后的单句/短语（去除多余空格、统一大小写），而非整段文本
- **区分是否缓存**：直译结果适合缓存（较稳定）；语法解释/风格化译文默认不缓存，或提供"强制重新生成"开关
- **失效策略**：LRU（最近最少使用）+ 过期时间，避免无限增长
- **缓存 key 包含模型版本 + prompt 版本**：换模型或改 prompt 后，旧缓存自动失效
- 存储：本地 SQLite 即可，无需引入 Redis

### 3.4 翻译历史存储
用 SQLite 存储，为后续 RAG（检索历史翻译/术语一致性）打基础：

```
translations 表字段：
- id
- timestamp
- source_text
- target_lang
- mode              (quick / detailed)
- literal_translation
- grammar_analysis  (JSON)
- explanation
- model_used
- tokens_used
```

## 四、技术栈

- **语言**：Python（RAG、embedding、Anthropic SDK、MCP SDK 生态都比较成熟）
- **存储**：SQLite（翻译历史 + 缓存）
- **向量检索**：待阶段4确定（如 chromadb）
- **架构形态**：**暂不做前后端分离**
  - 阶段0-5：全部用 CLI（命令行），专注打磨"大脑"逻辑，不被前端分心
  - 阶段6-7：MCP 本身是 client-server 架构，会自然长出雏形
  - 阶段8：视需求决定是否做网页 UI（可选 Streamlit/Gradio 快速原型，或 FastAPI 正式前后端分离）

## 五、分阶段路线图

| 阶段 | 内容 | 学习重点 |
|---|---|---|
| 0 | 环境搭建：文件夹结构、git init、虚拟环境、依赖管理、API key 管理 | 项目工程化基础 |
| 1 | 核心直译：封装 API 调用（含 provider 抽象层）、CLI 输入输出、基础翻译 prompt | system prompt 设计 |
| 2 | 扩展分析功能：直译 + 语法分析，结构化 JSON 输出，quick/detailed 模式切换 | 结构化输出、多任务 prompt |
| 3 | 融合老词库：接入开源词库，设计词库与 AI 的协同策略 | 数据源路由逻辑 |
| 4 | RAG：翻译历史 + 词库 embedding 化，检索后注入 prompt | embedding、向量检索、chunk 策略 |
| 5 | 自定义工具（Tool Use）：让模型自主决定调用"查词典""查术语库"等工具 | tool schema、多轮工具调用循环 |
| 6 | MCP：把阶段5的工具封装成独立 MCP Server | MCP 协议、server/client 架构 |
| 7 | Agent 化：自动判断文本类型 → 选策略 → 分段翻译 → 自我校对 | agent loop、状态管理 |
| 8 | 打磨：日志、可观测性、缓存/历史落地、（可选）简单 UI、测试 | 工程化收尾 |
