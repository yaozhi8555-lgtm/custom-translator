# 定制化翻译软件 · 开发计划

> 本项目的核心目的不是"做出一个翻译软件"，而是通过实战把 Prompt Engineering、RAG、Tool Use、MCP、Agent 编排这些技术串联起来，最终具备为企业构建 Agent 系统的能力。
> 计划会随开发进度不断调整，本文档是当前阶段的共识记录，不是一成不变的规范。

---

## 一、项目背景

市面翻译软件的痛点：
- 只能直译，无法做句子结构分析、语法讲解等深度解析
- 词库老旧，且不开放接自定义 AI 模型接口，用几次就要求付费
- 希望做到：老词库 + 自定义 AI API + Prompt 定制化，三者结合

**开发方式**：使用 Claude Code 作为编码助手，采用"一边学习一边构建"的方式，不追求一步到位生成可用软件，而是每一步都要理解代码在做什么。

## 二、产品设计决策

### 2.1 输入形式
- 当前阶段：仅支持**纯文本**输入
- 暂不做：文档（docx/pdf）、网页翻译（留待后续扩展）

### 2.2 输出形式：结构化输出
不用一整段夹杂译文+解释的文本，而是让 AI 按固定 schema 返回结构化数据（JSON），每个字段独立可用，方便后续 UI 渲染和工具联动（如生成 Anki 卡片、导出 Markdown 笔记）。

**Phase2 最终确定的 detailed 输出结构**：

```json
{
  "translation": {
    "literal": "逐字直译结果",
    "meaning": "更自然的意译结果",
    "difference": "直译和意译的区别及各自适用场合"
  },
  "sentence_structure": [
    {
      "component": "主语 / 谓语 / 定语从句 / 虚拟语气 等",
      "original": "原文对应片段",
      "explanation": "详细语法解释"
    }
  ],
  "special_grammar": "虚拟语气、倒装、省略等特殊语法说明，没有则为空字符串",
  "vocabulary": [
    {
      "word": "重点单词 / 俚语 / 固定搭配",
      "type": "单词 / 俚语 / 固定搭配 / 惯用表达",
      "meaning": "含义和用法说明",
      "examples": ["例句1", "例句2"]
    }
  ],
  "overall_note": "整体评注：语气、使用场景、文化背景、近义表达程度差异等",
  "other_languages": {}
}
```

### 2.3 翻译模式：按需生成
通过参数控制返回内容的详细程度：

| 模式 | 返回内容 | 适用场景 |
|---|---|---|
| `quick` | 仅直译 | 整段/整篇快速翻译 |
| `detailed` | 直译+意译+句子结构+特殊语法+重点词汇+整体评注 | 单句/短语深度学习 |

CLI 调用方式：
```bash
python -m translator.cli "文本" --from 中文 --to 英文 --mode detailed
```

### 2.4 语言支持
- 当前支持：中英互译（`--from` 指定原文语言，`--to` 指定目标语言）
- 预留扩展：`DetailedResult` 里有 `other_languages` 字段（`dict[str, str]`），以后加日文/韩文等直接往里填，不需要改数据结构

## 三、技术架构决策

### 3.1 老词库的定位：RAG 检索源
词库不再是"翻译结果的来源"，而是**AI 翻译前的参考上下文**：
1. 老词库（如 CC-CEDICT 等开源词典）做向量化，建立可检索库
2. 翻译时先检索相关词条（尤其是多义词、专业术语）
3. 检索结果作为上下文注入 prompt，让 AI 结合语境判断，而非仅凭训练记忆直译

### 3.2 API Provider 抽象层

**决策更新**：实际调用走 **OpenRouter**（原因：统一计费入口、价格更划算，而非需要同时对比多家模型效果）。

OpenRouter 是聚合网关，对外接口**兼容 OpenAI 格式**，因此：
- 依赖包安装 `openai`（而非 `anthropic`），`base_url` 指向 OpenRouter：
  ```python
  from openai import OpenAI
  client = OpenAI(
      base_url="https://openrouter.ai/api/v1",
      api_key=os.getenv("OPENROUTER_API_KEY"),
  )
  ```
- 模型名要写成 `厂商前缀/模型名`，如 `anthropic/claude-sonnet-4.5`
- 返回结构走 `response.choices[0].message.content`（OpenAI 风格），与直连 Anthropic SDK 的 `message.content` 结构不同

因为当前只走 OpenRouter 一个入口，**provider 抽象层可以先简化**：阶段1只需扎实实现"OpenRouter provider"这一个，抽象层留好接口即可，以后要接别的服务商（如直连 Anthropic 官方 API 用某些独有功能）时再加新的 provider 实现类：

```python
translate(text, provider="openrouter")   # 预留接口，后续可扩展 "anthropic_direct" / "ollama" 等
```

由于目标是"划算"，**成本控制（缓存、token 用量统计）比最初设想的更重要**，是真正要在阶段0-8持续关注的点，而不只是顺手加的功能。

### 3.3 缓存机制：轻量、非全量
- **缓存粒度**：标准化后的单句/短语（去除多余空格、统一大小写），而非整段文本
- **区分是否缓存**：直译结果适合缓存（较稳定）；语法解释/风格化译文默认不缓存，或提供"强制重新生成"开关
- **失效策略**：LRU（最近最少使用）+ 过期时间，避免无限增长
- **缓存 key 包含模型版本 + prompt 版本**：换模型或改 prompt 后，旧缓存自动失效
- 存储：本地 SQLite 即可，无需引入 Redis

### 3.4 翻译历史存储
用 SQLite 存储，为后续 RAG（检索历史翻译/术语一致性）打基础：

```
translations 表字段：
- id
- timestamp
- source_text
- target_lang
- mode              (quick / detailed)
- literal_translation
- grammar_analysis  (JSON)
- explanation
- model_used
- tokens_used
```

## 四、技术栈

- **语言**：Python（RAG、embedding、Anthropic SDK、MCP SDK 生态都比较成熟）
- **存储**：SQLite（翻译历史 + 缓存）
- **向量检索**：待阶段4确定（如 chromadb）
- **架构形态**：**暂不做前后端分离**
  - 阶段0-5：全部用 CLI（命令行），专注打磨"大脑"逻辑，不被前端分心
  - 阶段6-7：MCP 本身是 client-server 架构，会自然长出雏形
  - 阶段8：视需求决定是否做网页 UI（可选 Streamlit/Gradio 快速原型，或 FastAPI 正式前后端分离）

### 阶段3：融合老词库 ✅
**新增文件**：
- `dictionary/loader.py` — 解析 CC-CEDICT，`DictEntry` 数据结构（去掉拼音字段，保留繁体用于检索）

**修改文件**：
- `config.py` — 新增 `DICT_PATH`、`DICT_DB_PATH`、`MAX_DICT_RESULTS`、`MIN_WORD_LENGTH`

- `core.py` — 翻译前先查词典，把词条上下文注入 prompt

> **设计决策**：`DictEntry` 去掉了拼音字段（中英互译用不上，注入 prompt 是噪音），但解析时仍需读过拼音才能拿到释义；繁体字段保留但只用于检索，不出现在 prompt 上下文里。
